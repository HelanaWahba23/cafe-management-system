# Implementation Plan: Menu and Table Management

**Branch**: `master` (actual Git branch; no branch created) | **Date**: 2026-10-25 | **Spec**: [spec.md](spec.md)

**Input**: Approved feature specification, `requirements.md`, Constitution v1.0.1,
clarification answers, and the approved Blazor/Bootstrap technology change.

## Summary

Add a .NET 8 Blazor Web App frontend to the existing ASP.NET Core 8 Web API host, using
Interactive Server for interactive screens and locally served Bootstrap responsive styles.
Retain controller APIs and Swagger. Both controllers and server-rendered components call the
same small application services. Use SQL Server, EF Core, ASP.NET Core Identity and QRCoder.
One existing project and one process are sufficient: no extra frontend server, client runtime
project, internal HTTP loopback, generic repository, mediator or separate domain assemblies.

Admin creates/views/edits categories, products, prices, availability and tables. Public mobile
menu browsing is anonymous; QR links select table context and unavailable products are hidden.
Ordering, payment processing, POS, reports, delivery, deletion and deactivation remain excluded.

## Technical Context

**Language/Version**: C# 12, .NET 8 / ASP.NET Core 8 Blazor Web App; Bootstrap 5.3.x pinned
locally (5.3.8 researched baseline). No separate frontend compilation toolchain required.

**Primary Dependencies**: Existing Swashbuckle.AspNetCore 6.4.0 retained initially; EF Core
SqlServer, Design, Identity.EntityFrameworkCore and dotnet-ef compatible 8.0.x servicing versions;
QRCoder 1.8.1. Blazor Interactive Server is supplied by the ASP.NET Core shared framework.
Pin exact compatible package/static-asset versions and retain Bootstrap license at implementation.

**Storage**: One SQL Server CafeManagement database and CafeDbContext derived from
IdentityDbContext. Use IDbContextFactory<CafeDbContext> for management/public query operations;
create and dispose one context per operation, never keep one in a component/circuit.

**Testing**: Solution restore/build, Release build/publish verification and focused manual
functional/security/mobile/reconnection review. No automated tests generated by default.

**Target Platform**: Existing Windows development host and modern mobile/desktop browsers.
One HTTPS origin serves controllers, Blazor, static assets, account pages and the Blazor circuit.
Interactive use needs a reliable network connection and server circuit support. No deployment now.

**Project Type**: Combined Web API and Blazor Web App in the current Web SDK project.

**Performance Goals**: SC-001–SC-008 on a small portfolio dataset at 360/390/1280px. No invented
throughput/uptime promises. Project public reads to available products only; no cache layer.

**Constraints**: Three-day AI-assisted overall project, simple folders and services. Do not
spend all three days on this first feature or imply the full portfolio is already deliverable.
Preserve existing code except necessary additive integration; no speculative business rules.

**Scale/Scope**: One cafe, three domain entities, login and anonymous browsing. Admin may
manage; Cashier may authenticate but cannot access Admin operations and gets no POS screen here.

### Existing project inspection and necessary future changes

- The current solution has one net8.0 Web SDK API project, WeatherForecast controller/model,
  Swagger, startup, logging, launch profiles and sample HTTP request. No cafe code or UI exists.
- Preserve existing controller/model/sample behavior, ports and logging. Do not run a project
  template over the repository or replace Program.cs wholesale.
- Add Razor components/Interactive Server services and component endpoints, Razor Pages for
  account HTTP forms, static file serving, Identity/authorization, antiforgery and factory-backed
  persistence registration. Authentication precedes authorization; antiforgery follows both.
- Use .NET 8-compatible AddRazorComponents/AddInteractiveServerComponents,
  MapRazorComponents/AddInteractiveServerRenderMode, AddRazorPages/MapRazorPages and UseStaticFiles.
  Avoid newer-framework APIs and a blanket HTML fallback over controller/API paths.
- Keep existing controllers mapped. Unknown /api routes must not return component HTML. Blazor
  supplies component routes and circuit endpoints; public deep links must work on direct loads.
- Read-only prior inspection found SDK 8.0.400/runtime 8.0.8 and named SQL service
  MSSQL$MSSQLSERVER01 running. Connectivity, SQL permissions/version and HTTPS phone access remain
  unverified. No build, install, migration or source modification performed during planning.

### Application boundaries and authentication

Components use AuthenticationStateProvider for the trusted server-side circuit principal;
controllers use their HTTP User. Both pass that trusted principal to the same management
service boundary. Each operation performs Admin authorization, not just a UI visibility check.
Use a small helper and a fresh Identity scope to verify the current user, security stamp and
Admin role for protected operations; do not trust browser-supplied roles or a circuit-time
IHttpContextAccessor. Public menu reads never depend on an authenticated principal.

Login/logout are ordinary Razor Page HTTP form requests with antiforgery and Identity
SignInManager; cookie changes cannot be made from a live interactive event after headers are
sent. A full browser navigation creates a fresh circuit after login/logout. Interactive admin
pages use the Identity revalidating AuthenticationStateProvider pattern. Periodic circuit
revalidation alone is not an instant revocation guarantee; per-operation checks remain required.

Factory context options must be registered consistently with Identity's HTTP-scoped stores.
Use factory-created contexts for domain operations and short scopes for circuit-initiated
Identity checks; never retain scoped UserManager/Identity stores in long-lived components.
